# План разработки сервиса поиска по видеолекциям

## 1. Назначение документа

Это задание для ИИ-исполнителя, который будет реализовывать проект. Основа — ТЗ хакатона «Киберрывок 2026» на семантический поиск по видеолекциям. В план также включены роли и дополнительные функции, выбранные заказчиком.

**Ожидаемый результат:** работающее веб-приложение, исходный код в Git-репозитории, инструкция по запуску и презентация со скриншотами для жюри. По расписанию исходного ТЗ защита проходит 28 октября 2026 года с 14:30 до 16:30.

**Как читать требования:** пункты исходного ТЗ и дополнения заказчика объединены ниже в один объём реализации. В самом ТЗ поиск по нескольким лекциям, «Вопрос-ответ», выделение терминов, импорт из внешних источников и офлайн-режим названы дополнительными возможностями. Заказчик выбрал первые четыре из них для реализации, а также добавил роли, предложения видео, закладки и заметки. Офлайн-режим с локальными моделями остаётся вариантом реализации, но не отдельным обязательным сценарием этого плана.

Перед реализацией исполнитель должен изучить существующий репозиторий и его инструкции. Если проекта ещё нет, создать его с нуля. Не заменять рабочие части проекта без необходимости. Если для функции нужен внешний ключ или сервис, реализовать интеграцию и явно указать, какие данные нужны от заказчика.

## 2. Цель продукта

Пользователь загружает или открывает видеолекцию, после чего система получает транскрипт с таймкодами. Пользователь задаёт запрос на обычном языке и получает подходящие фрагменты лекции. Нажатие на результат открывает видео в нужный момент. У лекции также есть конспект, оглавление, ключевые термины, вопросы и личные заметки.

## 3. Обязательный объём работ для этого проекта

В готовом приложении должны быть реализованы все пункты ниже:

1. Личный кабинет и три роли: **зритель**, **преподаватель**, **администратор**.
2. Разграничение прав на сервере.
3. Загрузка MP4/WebM преподавателем или администратором.
4. Импорт видеолекции по ссылке из YouTube или Vimeo с понятной обработкой случая, когда источник не даёт получить аудио или субтитры.
5. Извлечение аудио, распознавание речи, сохранение текста с таймкодами до секунды.
6. Семантический индекс и поиск по смыслу, включая поиск сразу по нескольким лекциям.
7. Результаты поиска с фрагментом текста, названием лекции и переходом к таймкоду.
8. Видеоплеер, синхронизированный транскрипт и переход по клику на фрагмент текста.
9. Автоматический краткий конспект и оглавление лекции с таймкодами разделов.
10. «Вопрос-ответ» по содержанию лекции с указанием подтверждающих фрагментов и таймкодов.
11. Выделение ключевых терминов и переход к местам, где они встречаются.
12. Личные закладки и заметки, привязанные к таймкоду.
13. Предложение видео зрителем и рассмотрение предложения администратором.

## 4. Пользователи и права

При регистрации пользователь получает роль `viewer`. Роли `teacher` и `admin` назначает только администратор. Создание первого администратора выполняется через отдельную команду начальной настройки или переменные окружения; публичная регистрация администратора запрещена.

| Действие | Зритель (`viewer`) | Преподаватель (`teacher`) | Администратор (`admin`) |
|---|:---:|:---:|:---:|
| Смотреть доступные лекции, транскрипты и конспекты | Да | Да | Да |
| Искать по одной или нескольким лекциям | Да | Да | Да |
| Задавать вопросы по лекции | Да | Да | Да |
| Создавать свои закладки и заметки | Да | Да | Да |
| Предлагать видео для добавления | Да | Да | Да |
| Загружать и импортировать лекции | Нет | Да | Да |
| Редактировать и удалять свои лекции | Нет | Да | Да |
| Редактировать и удалять любые лекции | Нет | Нет | Да |
| Рассматривать предложения о добавлении видео | Нет | Нет | Да |
| Назначать роли и управлять пользователями | Нет | Нет | Да |

Скрытие кнопки в интерфейсе не считается защитой: каждый соответствующий запрос к API должен проверять авторизацию, роль и принадлежность лекции. Личные заметки доступны только их владельцу.

## 5. Сценарии работы

### 5.1. Зритель

1. Входит в личный кабинет.
2. Открывает каталог и выбирает одну лекцию или весь курс.
3. Вводит запрос, например: «объяснение теоремы Пифагора».
4. Видит найденные фрагменты с названием лекции, текстом и таймкодом.
5. Нажимает на результат и попадает в нужное место видео.
6. Может задать вопрос по лекции, открыть конспект, сохранить закладку и написать заметку.
7. Может предложить ссылку на новую лекцию; предложение попадает в очередь администратора.

### 5.2. Преподаватель

1. Загружает MP4/WebM или добавляет ссылку на YouTube/Vimeo.
2. Указывает название, описание и при необходимости название курса.
3. Видит состояние обработки: `queued`, `processing`, `ready`, `failed` или `needs_transcript`.
4. После обработки проверяет видео, транскрипт, поиск, конспект и оглавление.
5. Может исправить метаданные своей лекции и удалить её.

### 5.3. Администратор

1. Видит список пользователей и назначает роли.
2. Видит все лекции и их состояние.
3. Рассматривает предложения зрителей: одобряет, отклоняет с причиной или оставляет в очереди.
4. Может импортировать одобренную ссылку как лекцию и управлять любым материалом.

## 6. Функциональные требования

### 6.1. Лекции и импорт

- Поддержать загрузку файлов MP4 и WebM с проверкой типа и ограничением размера, заданным в конфигурации.
- Каждая лекция имеет уникальный ID, название, описание, автора, источник, состояние обработки, дату добавления и необязательную принадлежность к курсу.
- Импорт по ссылке принимает только поддерживаемые адреса YouTube/Vimeo. Система получает доступные метаданные и пытается получить субтитры либо аудио для обработки.
- Хотя в базовом требовании ТЗ упомянута загрузка файла **или** ссылка на видео, в этом проекте заказчик просит реализовать оба способа. Для доступной публичной ссылки импорт считается успешным только тогда, когда лекция обработана, ищется и воспроизводится с переходом по таймкоду. Поддержать управление временем воспроизведения и для встроенного плеера внешнего источника.
- Если конкретный источник не позволяет получить материал для транскрипции, показать статус `needs_transcript` и предложить преподавателю приложить файл видео или субтитров. Не отображать такую лекцию как готовую к поиску. Этот путь обработки ошибки не заменяет работающий импорт доступных ссылок.
- Долгая обработка идёт в фоновой задаче; пользователь видит состояние и понятную ошибку при сбое. Повторный запуск обработки доступен преподавателю для своей лекции и администратору.

### 6.2. Транскрипт и таймкоды

- Извлечь аудио из файла и преобразовать речь в текст автоматической моделью распознавания.
- Хранить фрагменты в виде `start_seconds`, `end_seconds`, `text`.
- Таймкоды округлять для отображения до секунды; исходные значения сохранять с достаточной точностью для перехода в плеере.
- При загрузке доступных SRT/VTT использовать их как источник транскрипта без повторного распознавания.
- По клику на строку транскрипта плеер переходит к её началу. Во время воспроизведения текущий фрагмент подсвечивается.

### 6.3. Семантический поиск

- Разбить транскрипт на содержательные части, сохранив для каждой начало и конец видео.
- Вычислить многоязычные эмбеддинги для частей и запросов.
- Искать по смысловой близости, а не только по буквальному совпадению слов.
- Пользователь может ограничить поиск текущей лекцией, выбранными лекциями либо всем доступным каталогом.
- Результат содержит название лекции, текстовый фрагмент, таймкод и кнопку перехода к видео.
- Не показывать результаты из лекций, к которым у пользователя нет доступа, если ограничения доступа будут добавлены позже.

### 6.4. Конспект, оглавление и термины

- Сформировать короткий конспект всей лекции.
- Сформировать разделы и подразделы с начальным таймкодом; каждый пункт оглавления открывает соответствующее место видео.
- Выделить ключевые термины и показать связанные с ними места транскрипта.
- Генерировать эти данные только после получения транскрипта. При повторной обработке лекции обновлять производные данные.

### 6.5. Вопрос-ответ

- Пользователь задаёт вопрос по одной лекции.
- Система сначала находит релевантные фрагменты транскрипта, затем формирует ответ на их основе.
- В ответе показываются ссылки на подтверждающие фрагменты с таймкодами.
- Если в лекции нет достаточных данных, система прямо сообщает об этом и не выдумывает ответ.
- История вопросов может храниться в рамках сеанса; постоянная история не обязательна для первой версии.

**Зависимость:** для качественной генерации ответов и конспекта нужен доступ к языковой модели. Предпочтительный путь для быстрой реализации — API, ключ которого заказчик передаст перед запуском этих функций. Альтернатива — локальная модель, если есть подходящие ресурсы сервера. Ключ хранить только в переменных окружения на сервере; не передавать его в браузер и не добавлять в репозиторий. Для распознавания речи и эмбеддингов допустимы локальные модели.

### 6.6. Закладки, заметки и предложения

- Закладка хранит пользователя, лекцию, таймкод, необязательное название и дату создания.
- Заметка хранит пользователя, лекцию, таймкод и текст. Её можно изменить или удалить.
- В личном кабинете показывать закладки и заметки с переходом в видео.
- Предложение видео хранит ссылку, комментарий автора, автора, дату, статус (`pending`, `approved`, `rejected`) и при отказе причину.
- Одобрение предложения не должно создавать две одинаковые лекции при повторном нажатии.

## 7. Экраны приложения

1. **Вход и регистрация.** Новому пользователю назначается роль зрителя.
2. **Каталог лекций.** Список, поиск, фильтр по курсу и состояние обработки для владельца материала.
3. **Страница лекции.** Плеер, синхронный транскрипт, оглавление, конспект, термины, вопрос-ответ, закладки и заметки.
4. **Общий поиск.** Запрос и выбор одной, нескольких или всех лекций; результаты с переходами к таймкодам.
5. **Личный кабинет.** Данные пользователя, его закладки, заметки, предложения; для преподавателя — его лекции и форма добавления.
6. **Панель администратора.** Пользователи и роли, все лекции, очередь предложений.

Интерфейс должен быть на русском языке. Ошибки должны объяснять следующее действие пользователя, например: «Не удалось получить субтитры по ссылке. Загрузите файл видео или SRT/VTT».

## 8. Рекомендуемая реализация

Конкретный стек можно сохранить из существующего репозитория. Если проект создаётся с нуля, использовать следующий вариант, чтобы сократить число архитектурных решений:

- **Frontend:** React + TypeScript, плеер с управлением временем воспроизведения.
- **Backend:** Python + FastAPI.
- **База данных:** SQLite для демонстрации; структуру данных сделать пригодной для последующего перехода на PostgreSQL.
- **Хранение видео:** локальная директория, вынесенная в конфигурацию.
- **Обработка:** FFmpeg для аудио, локальная модель распознавания речи или подключаемый API.
- **Поиск:** многоязычная модель эмбеддингов и векторный индекс; запись о каждом фрагменте связана с ID лекции и таймкодом.
- **Фоновые задачи:** отдельный обработчик с сохранением состояния задач в базе данных.
- **Генерация конспекта и ответов:** адаптер языковой модели, конфигурируемый через переменные окружения.
- **Авторизация:** серверная сессия или защищённый HttpOnly cookie; пароли хранить только в виде надёжных хешей.

Минимальные сущности данных: `User`, `Lecture`, `Course`, `ProcessingJob`, `TranscriptSegment`, `SearchChunk`, `OutlineSection`, `KeyTerm`, `Bookmark`, `Note`, `VideoSuggestion`. Связи с пользователем и лекцией должны быть явными. Удаление лекции должно удалять или отвязывать её файлы, транскрипт, индекс и производные данные согласованно.

3. Реализовать каталог, загрузку видео, страницу лекции и хранение файлов.
4. Добавить фоновую транскрипцию и сохранение сегментов с таймкодами.
5. Реализовать семантический индекс, поиск по одной лекции и переход к найденному месту.
6. Расширить поиск на несколько лекций и весь каталог.
7. Добавить конспект, оглавление и ключевые термины.
8. Добавить вопрос-ответ с подтверждающими таймкодами.
9. Реализовать закладки, заметки, предложения видео и панель администратора.

11. Подготовить README с запуском, перечнем переменных окружения, описанием ролей и ограничений. Подготовить демонстрационные материалы и скриншоты для защиты.

Если для следующего этапа требуется API-ключ, продолжать независимые этапы и запросить ключ только тогда, когда интеграция готова к подключению. Не подменять неработающую функцию демонстрационной заглушкой без явной пометки.

## 10. Критерии готовности

Проект готов к представлению, когда выполняются следующие сценарии:

- Зритель входит, находит лекцию, смотрит видео, задаёт смысловой запрос и переходит из результата к правильному моменту.
- Тот же зритель ищет по нескольким лекциям, сохраняет закладку и заметку, затем открывает их из личного кабинета.
- Преподаватель загружает MP4/WebM, видит ход обработки, а после завершения — транскрипт, результаты поиска, конспект и оглавление.
- Преподаватель добавляет поддерживаемую внешнюю ссылку; при недоступном аудио или субтитрах получает понятный следующий шаг.
- Для поддерживаемой публичной ссылки, из которой доступны аудио или субтитры, импорт завершается состоянием `ready`: лекция воспроизводится, находится поиском, а переход к таймкоду работает.
- Вопрос-ответ даёт ответ с подтверждающими таймкодами либо сообщает, что ответа в материале нет.
- Зритель отправляет предложение видео, администратор видит и рассматривает его.
- Зритель не может вызвать API загрузки или изменить чужую заметку; преподаватель не может управлять пользователями или чужими лекциями.
- Проект запускается по README, а секретные ключи отсутствуют в Git-репозитории.

## 11. Материалы для жюри

Согласно ТЗ, к защите нужны рабочий прототип, Git-репозиторий, краткая инструкция по запуску и презентация со скриншотами. В презентации показать проблему, решение, архитектуру, живой сценарий поиска с переходом к таймкоду, роли пользователей и дополнительные функции. Для демонстрации подготовить минимум одну заранее обработанную лекцию, чтобы показ не зависел от времени распознавания нового видео.

Основные критерии оценки из ТЗ: работоспособность, удобство интерфейса, качество смыслового поиска, стабильность, полезность дополнительных функций и ясность презентации.
